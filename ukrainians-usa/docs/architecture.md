# Архитектура: мультигородская модель

Главный архитектурный принцип проекта. Заложить его нужно с первого дня —
достраивать потом дорого.

## Проблема, которую решаем

Наивный подход «сделаем Сиэтл, потом скопируем на Сакраменто» разваливается на
третьем-четвёртом городе: контент дублируется, обновление правила по EAD
требует правок в 10 местах, часть копий устаревает незаметно.

## Решение: три слоя контента

Каждая единица контента привязана не к городу, а к **уровню видимости**.

| Уровень | Что сюда попадает | Пишется |
|---|---|---|
| **Federal** | USCIS, EAD, парол/TPS, SSN, федеральные налоги, иммиграционные новости | Один раз на всю страну |
| **State** | Права, Medicaid, пособия штата, налоги штата, страховка авто, школы | Один раз на штат |
| **Metro** | НКО, церкви, специалисты, события, чат, барахолка, нужды | Один раз на метро |

Пользователь видит объединение трёх слоёв, релевантных его локации:

```
Сиэтл      → Federal + WA + Seattle Metro
Сакраменто → Federal + CA + Sacramento Metro
```

### Экономический эффект

Ориентировочное распределение объёма контента:

- **~60% federal** — пишется один раз, работает во всех 50 штатах
- **~30% state** — пишется один раз на штат
- **~10% metro** — единственное, что пишется для каждого города

Стоимость запуска нового города:

| Сценарий | Нужно написать |
|---|---|
| Новое метро в уже покрытом штате (Спокан после Сиэтла) | ~10% |
| Новое метро в новом штате (Портленд) | ~40% |
| Первый город (Сиэтл) | 100% |

## Гео-иерархия

```
Country (USA)
 └── State (WA, CA, IL, OR, PA, ...)
      └── Metro (Seattle–Tacoma, Spokane, ...)
           └── Sub-area (South King County, Snohomish, Eastside)
```

**Sub-area** не нужна в первой версии интерфейса, но должна быть в модели
данных сразу. В Сиэтле она уже актуальна: человеку из Everett неинтересна
барахолка в Federal Way. В маленьком метро этот уровень просто остаётся пустым.

Объекты привязываются к метро, но хранят координаты — чтобы позже можно было
сортировать по реальному расстоянию, а не только по названию района.

## Определение локации пользователя

**Онбординг:**

```
язык (UA/RU/EN) → ZIP-код → авто-определение state + metro
→ иммиграционный статус → интересы
```

ZIP-код, а не выбор города из списка. Причины:

1. Быстрее и точнее для пользователя
2. Работает для тех, кто живёт в пригороде и не знает, к какому «метро»
   относится
3. **Даёт карту реального расселения** — по ней приоритизируется следующий
   город, вместо догадок

Переключатель города доступен из шапки в любой момент, плюс режим «по всей
стране» (люди переезжают, ищут заранее, имеют родню в других штатах).

## Города, которые ещё не запущены

Пользователь из непокрытого города **не должен упереться в пустой экран**.

Он получает:
- Federal-слой полностью
- State-слой, если штат уже покрыт
- Вместо Metro-слоя — экран ожидания: «Мы ещё не запустились в Хьюстоне.
  Оставь email» + счётчик «уже 47 человек из Хьюстона ждут»

Этот экран одновременно:
- удерживает пользователя вместо оттока
- собирает лист ожидания
- даёт данные для приоритизации следующего запуска

## Playbook запуска города

Запуск оформлен как повторяемый чеклист. Цель — чтобы 5-й город открывался за
неделю силами волонтёра, а не за три месяца силами основателя.

- [ ] Метро заведено в БД, ZIP-коды привязаны
- [ ] State-слой готов (если штат новый — 8–10 гайдов)
- [ ] Metro-слой: 15–20 проверенных организаций, церквей, специалистов
- [ ] Найдены 1–2 локальных модератора **до** открытия
- [ ] Есть партнёр-НКО, готовый рассказать о приложении своим клиентам
- [ ] В листе ожидания минимум ~100 человек из этого метро

**Жёсткое правило: город не открывается без модератора.** Немодерируемый чат
портит репутацию всей платформы, а не только одного города.

## Стратегия расширения

Не спешить со вторым городом. 2000 активных пользователей в одном Сиэтле
ценнее, чем 200 в десяти городах: плотность сообщества и есть продукт. Если
человек опубликовал нужду и никто не ответил — он не вернётся.

**Критерий готовности к расширению:** Сиэтл живёт без ежедневного участия
основателя.

Порядок следующих городов определяется картой ZIP-кодов из листа ожидания.
Гипотеза на сегодня: Спокан или Ванкувер (WA) — тот же штат, State-слой готов,
значит стоимость запуска минимальна.

## Что это меняет в объёме MVP

Почти ничего — примерно 3–4 дополнительных дня работы:

- гайды размечаются federal/state/metro при написании (дисциплина, не код)
- каналы чата привязаны к scope, а не захардкожены под Сиэтл
- онбординг через ZIP вместо хардкода
- экран-заглушка для незапущенных городов

Экономия при масштабировании — месяцы.
